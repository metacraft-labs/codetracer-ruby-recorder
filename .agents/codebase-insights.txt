flake.nix defines a pre-commit check using git-hooks.nix. Run 'nix develop' to install git hooks.

The native tracer (Rust extension) caches frequently used Ruby method IDs and
class constants in the `Recorder` struct. When adding new Ruby method calls,
ensure the IDs are interned once during allocation and stored in the struct for
reuse.

A Ruby exception raised INSIDE the recorder used to wedge the recorded process,
and the structure that prevents it is not optional. `rb_raise` (and every Ruby
method that raises, and `rb_num2long` on a Bignum, and `rb_string_value_cstr` on
a String containing a NUL) `longjmp`s past every Rust frame WITHOUT running
destructors, so a live `MutexGuard` on `Recorder.tracer` was never released and
the next `flush_trace` blocked forever. Symptom to recognise: `/proc/<pid>/wchan`
== `futex_wait_queue`, no listening socket, no output at all.

The rule now is structural, not a convention: **no Ruby code may run while a
`MutexGuard` on the tracer is live.** The writer lives in `GuardedTracer`
(module `tracer_lock` in `ext/native_tracer/src/lib.rs`) whose `Mutex` field is
private to that module, so the compiler — not a comment — is what stops you from
locking and then calling Ruby. `GuardedTracer::with` holds the guard OUTSIDE the
`rb_protect` region the writer is used from, so a raise at any depth returns
normally and the lock is released by ordinary scope exit; `protect` is the same
primitive without the lock, for narrowing the blast radius to a single value.
The trade-off to know about: a caught raise leaks whatever Rust allocations were
live at that instant (destructors are skipped), which is why the protected
regions are deliberately small.

Consequences worth remembering:

* New `rb_funcall`s inside a `with` body are safe by construction. New Ruby
  calls added OUTSIDE one hold no lock, so they are safe too. Adding a
  `Mutex<...>` field of your own re-opens the hazard.
* Prefer the non-dispatching C API when one exists: `rb_obj_class` instead of
  `rb_funcall(self, :class)`, `rb_thread_current()` instead of
  `rb_eval_string("Thread.current")` (the latter compiled and ran a Ruby snippet
  on EVERY traced event — it was also the single most expensive thing in the
  hook).
* `test/test_recorder_never_wedges.rb` covers one case per hazard SHAPE and
  supervises each recording with an external timeout, so a regression is a
  failing test rather than a hung suite.

RS-M6 (request spans) — two more things that cost real time:

* Loading a big framework INSIDE the recording is not viable.
  `require "action_controller/railtie"` under an armed event hook took over
  400 s (versus ~10 s untraced) — the hook fires per executed line and pays
  `rb_tracearg_path` + a String allocation before `should_ignore_path` discards
  it. `test-programs/web/serve.rb` therefore drives `CodeTracer::RubyRecorder`
  as a library (`new` / `start` / `stop` / `flush_trace`) and loads the
  framework first, instead of running under `bin/codetracer-ruby-recorder`,
  which arms the hook before it loads the program.

* No trace filter is needed for web recordings. `should_ignore_path` already
  drops `gems/` and `lib/ruby`, which is where Sinatra, Rails, Rack and the
  CodeTracer middleware live, so an eight-request Sinatra session is ~750 steps
  in three files. (The Python recorder needed a whole `trace_filter.toml` for
  the same milestone.)

Correlation markers — the shape to copy, and the one trap:

* The Ruby facade never calls `to_s`. `CodeTracer::Native.mark_correlation_send`
  hands `key:` / `show:` to the extension UNCONVERTED, because those are the
  traced program's own objects: converting them in Ruby would let an exploding
  `to_s` kill a program that only annotated itself. The extension renders them
  with `value_to_string_exception_safe`, before the tracer lock, which is also
  what lets a NUL-containing key through instead of raising.
  (`register_span`'s `metadata` DOES call `to_s` in Ruby — those are the
  middleware's own strings, not user values. The asymmetry is deliberate.)
* Nothing here decides what a marker IS. The `MarkerPayload`, the label
  interning table and the `corrmark.ns` index are built once in the shared
  writer library so ~20 recorders cannot drift; a drifted payload would produce
  markers that are INVISIBLE rather than broken. Do not add a label cache to
  this repo — hoist `ensure_marker_id` at the call site and pass `marker_id:`.
* `ct print --json-events` does NOT carry the IO metadata slot, so it cannot see
  markers. `ct print --markers --json-out` is the view that decodes them;
  `test/ct_print_support.rb#ct_print_markers` wraps it.
